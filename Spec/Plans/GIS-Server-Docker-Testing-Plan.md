# GIS Server Docker Testing Plan

This plan addresses [issue #38](https://github.com/peholmst/iDispatchX/issues/38): make it possible to run the GIS Server as a Docker container for manual testing, including a small subset of real NLS data for address lookups and map tiles.

## Goals

- Run GIS Server and all its dependencies in Docker for manual testing
- Include a small subset of real NLS data for address lookups and WMTS tiles
- E2E tests continue to use mocks — no changes to that setup
- Simple commands to start and stop the test stack

## Non-goals

- Dockerizing the GIS Data Importer (a separate concern, separate issue)
- CI/CD integration of the test stack
- Changing E2E test setup (E2E tests keep their mock GIS Server)

## Phase 1: Tile Fixtures

Generate the WMTS tile directory from existing sample data and commit it to the repository so the test container can bind-mount it without re-running the importer.

### Task 1.1: Generate Tile Fixtures from SampleData

**Status:** Not Started

**Description:**
Run the GIS Data Importer raster tile import against `SampleData/L3311F.png` and `SampleData/L3311F.pgw`. Write the output to `SampleData/tiles/` using `orthophoto` as the layer name (consistent with existing infrastructure documentation). Commit the generated tile files so they are part of the repository.

The tile directory structure expected by the GIS Server is:
```
SampleData/tiles/
  orthophoto/
    ETRS-TM35FIN/
      {zoom}/
        {row}/
          {col}.png
```

**Files to create/modify:**
- `SampleData/tiles/orthophoto/ETRS-TM35FIN/...` (generated by importer, committed)

**Acceptance Criteria:**
- [ ] `SampleData/tiles/` contains at least one `.png` tile under `orthophoto/ETRS-TM35FIN/`
- [ ] GIS Server health endpoint reports `orthophoto` under `tileDirectory.layers` when this directory is mounted

**Dependencies:** None

## Phase 2: Geocoding Seed Data

### Task 2.1: Create Geocoding SQL Seed Script

**Status:** Not Started

**Description:**
Create `Implementation/deploy/docker/test/seed-geocoding.sql` with SQL `INSERT` statements that populate the GIS database with a small, representative dataset for testing the geocoding endpoint. The data should cover the geographic area of the `L3311R.xml` sample file.

The script will be applied by a one-shot `gis-data-seeder` container after the GIS Server's health check passes (which confirms Flyway migrations have completed and the schema is in place).

The schema targeted is defined in `Implementation/shared/gis-database/src/main/resources/db/migration/V1__create_gis_schema.sql`.

**Minimum dataset:**
- At least 1 municipality (`gis.municipality`)
- At least 2 road segments (`gis.road_segment`) on the same municipality
- At least 5 address points (`gis.address_point`) distributed across those roads
- At least 2 named places (`gis.named_place`)

All coordinates must be in EPSG:4326, consistent with the schema definition.

**Files to create/modify:**
- `Implementation/deploy/docker/test/seed-geocoding.sql` (new)

**Acceptance Criteria:**
- [ ] Script applies without errors to a PostGIS database where Flyway V1 has been applied
- [ ] `GET /api/v1/geocode?q=<road-name>` returns non-empty results matching the seeded road
- [ ] `GET /api/v1/geocode?q=<place-name>` returns non-empty results matching a seeded named place

**Dependencies:** None

## Phase 3: Keycloak Configuration

### Task 3.1: Create Test Keycloak Realm JSON

**Status:** Not Started

**Description:**
Create `Implementation/deploy/docker/test/keycloak-test-realm.json` with the `idispatchx` realm for combined GIS Server + Dispatcher Client testing. Base it on the existing `Implementation/clients/dispatcher-client/docker/keycloak-realm.json` and add:

1. **`gis-server` OIDC client**: The GIS Server validates bearer tokens; it does not perform redirect flows. Register a client with `clientId: "gis-server"` suitable for token audience validation. The exact client settings (public vs. confidential, `bearerOnly`) should match the GIS Server's OIDC configuration as implemented in `GisServerConfig`.

2. **`Dispatcher` realm role**: A realm-level role named `Dispatcher`. This role must appear in the `roles` array claim of access tokens per the Security NFR.

3. **Test dispatcher user**: A user (e.g., `dispatcher`) with a known password and the `Dispatcher` role assigned. This user is for manual testing only.

The existing `dispatcher-client` registration from the base realm JSON is preserved unchanged.

**Files to create/modify:**
- `Implementation/deploy/docker/test/keycloak-test-realm.json` (new)

**Acceptance Criteria:**
- [ ] Keycloak imports the realm without errors
- [ ] GIS Server successfully fetches JWKS from `http://keycloak:8080/realms/idispatchx/.well-known/openid-configuration`
- [ ] A token obtained for the test dispatcher user is accepted by the GIS Server (HTTP 200 on an authenticated endpoint)
- [ ] JWT `roles` claim contains `Dispatcher`

**Dependencies:** None

## Phase 4: Test Docker Compose

### Task 4.1: Create `docker-compose-test.yml`

**Status:** Not Started

**Description:**
Create `Implementation/deploy/docker/docker-compose-test.yml` with a lightweight, single-instance testing stack. It differs from the production `docker-compose.yml` as follows:

| Aspect | Production compose | Test compose |
|--------|--------------------|--------------|
| GIS Server instances | 2 (HA) | 1 |
| Reverse proxy | nginx | None (ports exposed directly) |
| Keycloak | Not included | Included |
| Tile data | Docker volume | Bind-mount from `SampleData/tiles/` |
| DB credentials | `.env` file | Hardcoded in compose (test only) |
| Data seeding | Not applicable | `gis-data-seeder` one-shot service |

**Services:**

```
keycloak        — Keycloak 26.0.0, test realm imported at startup
gis-db          — PostGIS 17-3.5, postgres superuser (enables Flyway to CREATE EXTENSION)
gis-server      — GIS Server, single instance, depends on gis-db (healthy) and keycloak (healthy)
gis-data-seeder — One-shot postgis container; applies seed-geocoding.sql after gis-server is healthy
```

**Ports:**
- `8080` → GIS Server HTTP
- `8180` → Keycloak HTTP
- `5432` → PostGIS (optional, for debugging)

**Key configuration:**
- `GIS_OIDC_ISSUER=http://keycloak:8080/realms/idispatchx`
- `GIS_OIDC_CLIENT_ID=gis-server`
- `GIS_TILE_DIR=/tiles` (bind-mounted from `SampleData/tiles/` relative to compose file location)
- `GIS_CORS_ALLOWED_ORIGINS=http://localhost:5173` (allows Dispatcher Client dev server)
- All credentials are test-only constants; no secrets management needed

**Files to create/modify:**
- `Implementation/deploy/docker/docker-compose-test.yml` (new)

**Acceptance Criteria:**
- [ ] `docker compose -f docker-compose-test.yml up` starts all services without errors
- [ ] GIS Server health endpoint (`http://localhost:8080/health`) returns `{ "status": "UP" }` with database and tileDirectory components healthy
- [ ] Tile layer `orthophoto` appears in health response under `tileDirectory.layers`
- [ ] Geocoding endpoint returns results after `gis-data-seeder` completes
- [ ] Keycloak is reachable at `http://localhost:8180/realms/idispatchx`
- [ ] `gis-data-seeder` exits with code 0 after successfully applying the seed script

**Dependencies:** Tasks 1.1, 2.1, 3.1

## Phase 5: Convenience Scripts

### Task 5.1: Create `start.sh`

**Status:** Not Started

**Description:**
Create `Implementation/deploy/docker/test/start.sh`. The script must be run from the `Implementation/` directory (to match the context path used in `Dockerfile`). It:

1. Builds the GIS Server Docker image from `Implementation/`:
   ```bash
   ./mvnw package -pl servers/gis-server -am -DskipTests
   docker build -t idispatchx/gis-server -f servers/gis-server/Dockerfile .
   ```
2. Starts the test compose stack detached:
   ```bash
   docker compose -f deploy/docker/docker-compose-test.yml up -d
   ```
3. Polls `http://localhost:8080/health` until `status` is `UP` (or times out after 120 s)
4. Prints the service URLs on success

The script exits with a non-zero status if the build fails or if any service does not become healthy within the timeout.

**Files to create/modify:**
- `Implementation/deploy/docker/test/start.sh` (new, executable)

**Acceptance Criteria:**
- [ ] `./deploy/docker/test/start.sh` (run from `Implementation/`) brings up the full stack from a clean state
- [ ] Script exits with non-zero status on failure
- [ ] Service URLs are printed on success

**Dependencies:** Task 4.1

## Execution Notes

**Recommended execution order:**

1. **In parallel**: Tasks 1.1, 2.1, 3.1 — no dependencies between them
2. **Task 4.1** — depends on 1.1, 2.1, 3.1
3. **In parallel**: Tasks 5.1, 5.2 — both depend on 4.1
4. **Task 6.1** — documents the finished system (depends on 4.1, 5.1, 5.2)
5. **Optional**: Tasks 1.2, 4.2 — can be done at any time

**Note on the postgres superuser in test compose:**
Using the PostgreSQL superuser (`POSTGRES_USER=postgres`) for both the database and the GIS Server connection simplifies the test setup: Flyway's `CREATE EXTENSION` statements in V1 succeed without a separate init script. This is intentional for testing only and must not influence the production setup.

**Note on additional sample data:**
The user may provide more NLS map sheets to expand coverage. Task 1.2 tracks this. All provided data goes into `SampleData/`; the tile fixtures in `SampleData/tiles/` are re-generated and committed.
